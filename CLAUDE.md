# eChopdo (repo: pocketOS)

A personal family app, used mainly as an installed PWA. **Display name: eChopdo** (Gujlish: *chopdo* = the family account/record book, blessed at Chopda Pujan; renamed from "PocketOS" by the user's choice — use eChopdo in all user-visible text). Internal identifiers keep the old name on purpose: repo/Vercel project, `pocketos.*` localStorage keys, the member email domain. React 19 + Vite, `@supabase/supabase-js`, Recharts. Plain CSS in `src/index.css` — IBM Plex Sans/Mono; theme **"Slate"** (quiet greys + one soft indigo accent), dark by default with a **light theme** (⚙ Settings → Appearance: Dark / Light / System, see UI notes). No router: modules and their tabs live in `src/App.jsx`.

## Modules
PocketOS is a shell of independent modules (list in `src/lib/modules.js`; Will is hidden, see below), picked via the segmented module switcher in the topbar (persisted to `localStorage` as `pocketos.activeModule`). The shared `Topbar` (`src/components/Topbar.jsx`) holds brand + switcher; each module component in `src/App.jsx` (`BudgetModule`, `VaultModule`) passes its desktop tabs as children and its actions as `right` (Budget: the `HouseholdMenu` chip; Vault: a lock button). No account/sign-out UI in the header — Sign out lives at the bottom of Budget → Accounts & Categories (and on the lock screens). One owner (the Google login) plus optional **household member logins** (see "Household member logins"). Module names are single words, **no "Pocket" prefix**.
- **Budget** — the finance features. Tabs **Home** (dashboard, id `dashboard`) · **Entries** (transactions) · **Plan** · **Dues** · **Hisab**; Accounts & Categories (`settings`) is not a tab but opens from the ⚙ button beside the household chip. The user's focus is forward-looking: planning next month, not analysing the past. The Dashboard is deliberately limited to last / this / next month; next month is the plan (unlogged `recurring_items` at `expected_amount` + any actuals already logged). Swipe left/right changes month on Dashboard, Transactions and Plan (`useMonthSwipe` in `src/lib/useSwipe.js`). **Accounts are used as sub-category buckets** ("Bills", "Mutual Fund", "Amazon ICICI"…), not real bank balances: the Dashboard shows a "By account" card with money spent / received through each account in the selected month (positive amounts; next month from Plan items' accounts) and a "Most spent from" tile — never balances or net worth. `account_balances` / `account_balances_on` still exist but the UI doesn't use them.
- **Vault** — passwords & credentials (LastPass-like), tabs Passwords / Generator / Security. See "Vault" below.
- **Will** (hidden) — builds the user's mother's will (વસિયતનામું) in Gujarati and exports it as a PDF; tabs વિગત / કુટુંબ / મિલકત / વહેંચણી / PDF. **Not in the switcher**: opened by pressing and holding the PocketOS logo for 700 ms (`useLongPress` in `Topbar.jsx`, `onSecret`), then a fresh fingerprint (`vault.verifyUser`, master-password fallback). It appears in the switcher only while open (`HIDDEN_WILL` in `modules.js`) and is never saved as the last module. See "Will" below.

## Locking, one fingerprint
- Once the vault exists, the **whole app** sits behind the vault unlock: `Shell` shows `UnlockScreen` (VaultGate, auto fingerprint prompt) while `vault.status === 'locked'`, so Budget is protected too, and one fingerprint opens Budget, Vault and Will — never ask twice. The old separate app lock (`useAppLock`) only applies when no vault is set up, and is switched off automatically once one is (it caused the double prompt).
- Fingerprint is per phone *and* per web address: `fingerprintHere(unlockers)` (useVault.js) checks this origin's `pocketos.vaultCredential`; the unlock screen only offers/auto-prompts that one. After an unlock by master password/recovery code on a phone without one, `useOfferFingerprint` (App.jsx) asks once "Use your fingerprint next time?" ("Not now" remembered in `pocketos.fingerprintOfferDismissed`). ⚙ Settings has a **Security** card for the owner (fingerprint on/off for this phone, **Change master password** — asks for the current one first, then `vault.changePassword`, which only re-wraps the key).
- Idle auto-lock counts activity in every module (`onPointerDownCapture`/`onKeyDownCapture` on `.shell`); locks after 5 min idle or 60 s in the background, or via a module's lock button.
- **Reload / pull-to-refresh doesn't re-ask** (`src/lib/vaultSession.js`): on unlock the vault key is saved for this tab only — encrypted with a random non-extractable AES key kept in IndexedDB, the blob `{ uid, iv, data, active, hiddenAt }` in sessionStorage (cleared when the PWA is closed). On load `useVault` restores it unless it's past 5 min idle / 60 s background; `lock()` and sign-out clear it. Closing and reopening the app always asks. Members' `useAppLock` does the same with a plain `pocketos.appUnlocked` timestamp in sessionStorage.

## Back button (installed PWA)
- `src/lib/backNav.js`: `useBackButton` (once, in Shell) keeps one extra history entry so Android back lands in the app. Back closes the top overlay first (dialog → menus → will preview → last `.modal-bg`, by DOM convention), then the highest registered `useBackAction` (level 2: a module's tab → its first tab; level 1: module → Budget), then at the root shows "Press back again to close" and a second back within 2 s exits. New overlays should use `.modal-bg` / `.dialog-bg` so back closes them.

## Vault (zero-knowledge)
- **Never send plaintext to Supabase.** One random 256-bit vault key encrypts each item (AES-GCM, item id as associated data) in `src/lib/vaultCrypto.js`. Every field, including the item type, lives inside `vault_items.ciphertext`.
- **Item types** (LastPass-style) are defined in `src/lib/vaultTypes.js`: 19 types (password, passkey, secure note, contact, payment card, bank account, driver's license, passport, government ID, health/insurance/membership, Wi-Fi, email, messenger, database, server, SSH key, software license), each with its field list. The form, detail view, list subtitle, search and quick-copy button are all driven from it, so a new type or field is a registry edit only. Items without `type` (saved before types existed) are passwords. Field labels match LastPass's, so LastPass secure notes import as typed items (`typedFromLastPassNote`). The UI is `src/components/VaultItems.jsx`: + opens a type picker (full-screen on phones), and filter chips appear once there's more than one type.
- The vault key is stored only *wrapped*, once per unlocker in `vault_unlockers`: `password` (PBKDF2-SHA256, 600k iterations), `recovery` (32-char Crockford base32 code → HKDF), `prf` (per-device fingerprint: WebAuthn PRF extension output → HKDF). Lose all three and the data is unrecoverable, by design.
- Fingerprint credentials (`src/lib/webauthn.js`) are PocketOS's own WebAuthn credentials with `rp.id = location.hostname`, separate from Supabase's sign-in passkeys, so they work on any origin (incl. localhost), but are per-origin. PRF needs Chrome on Android or Safari on iOS 18+. No server-side signature verification: the PRF secret is what decrypts.
- State lives in `useVault` (`src/lib/useVault.js`), called from `Shell` so switching modules doesn't lock. Key held in memory only (refs); auto-locks after 5 min idle or 30 s in the background.
- **App lock**: superseded by the vault gate (see "Locking, one fingerprint"). `src/lib/useAppLock.js` / `AppLockScreen.jsx` remain only for a login with no vault yet. Budget data itself isn't encrypted; the gate is a privacy lock.
- Extras in `src/lib/vaultTools.js`: TOTP (RFC 6238, base32 or `otpauth://`), password generator (rejection sampling, no look-alike chars), LastPass CSV import (parsed and encrypted on device), Have I Been Pwned k-anonymity breach check (only 5 hex chars of the SHA-1 leave the device), clipboard auto-clear after 30 s.
- Autofill into other apps/sites is impossible from a PWA. Users copy and paste.

## Will (Gujarati વસિયતનામું)
- Purpose: the user's mother's will, fully editable in the app, transparent between her two children, PDF in **Gujarati only**. Content is typed in Gujarati; the app UI stays English. **Never put the family's real names or details in code, placeholders or tests** — they live only in the encrypted document.
- Storage: the whole will is ONE JSON document (`src/lib/willModel.js` → `emptyWill()`), encrypted with the **Vault key** via `vault.seal/unseal` (so the module needs the vault unlocked; it shows `VaultGate` otherwise). Tables `wills` (one row per user) and `will_versions` (encrypted snapshots `{ note, doc }` for "Save version"). `useWill` (`src/lib/useWill.js`) decrypts, auto-saves edits (800 ms debounce, saves queued so the first insert can't double), and manages versions.
- Text: `src/lib/willText.js` generates all Gujarati wording — standard clauses (`CLAUSES`, each with a key; users can switch off or reword any via `doc.clauses[key] = { off } | { text }`) plus tables for family, executors, assets by type, residuary, alternates (default: the beneficiary's descendants), minors' guardians, wishes, custom clauses, and the attestation/witness page. Identifiers (account/policy/Aadhaar numbers) are wrapped in invisible U+2063 markers so `printable()` keeps their digits as typed when the PDF uses Gujarati digits. Aadhaar is always printed masked.
- Checks: `src/lib/willChecks.js` (shares ≠ 100 %, missing residuary, minors without guardian, witness in the family list, nominee ≠ beneficiary, joint property, wishes that look like bequests). Modelled on problems found in the mother's earlier (2023, Yellow-app) will.
- PDF: `src/lib/willPrint.jsx` renders `WillDocument` into a body-level `#will-print`, waits for the **Noto Serif Gujarati** font (loaded on demand from Google Fonts), and calls `window.print()` → "Save as PDF". The browser shapes Gujarati correctly; JS PDF libraries don't, so don't switch to one. `@page` margin boxes print the signature line, "પાનું N / M" (Gujarati counter style) and the version date on every page; print CSS hides `#root` and forces white paper.
- UI: `src/components/will/` (WillModule, WillDetails, WillFamily, WillAssets, WillSplit with the per-person "who gets what" summary, WillPdf = review tab with checks, full-screen preview → PDF, change log, versions, clause editor and import; WillDocument, WillParts). **All will UI is Gujarati-first** ("ગુજરાતી · English" labels) with a plain-Gujarati `hint`/`<Help>` line explaining each field, because the will-maker fills it in herself. Keep new fields that way.
- Special instructions: each asset's `note` and `doc.residuaryNote` print as "ખાસ સૂચના: …" (e.g. transfer a flat into someone's name). Wishes are separate and non-binding.
- Change log: `will_log` table, encrypted entries `{ start, end, changes[] }`. `useWill.writeLog` diffs each save against the session baseline with `diffWill` (`src/lib/willDiff.js`, Gujarati sentences, key-order-insensitive); edits within 30 min merge into one entry; the first save and imports are standalone entries.
- Import: the review tab (and the empty Details tab) import a `.json` `{ pocketosWill: 1, doc }` replacing the will. Used once to prefill from the 2023 will — that file was generated outside the repo and must never be committed.

## Android app (quick-add widget)
- `android/` (Kotlin, no Compose; see `android/README.md`): a Trusted Web Activity wrapping the web app (`MainActivity` launches it in Chrome explicitly, with an on-screen error/crash report if it fails — v1.0's stock LauncherActivity opened nothing on the owner's phone; same origin → same login/fingerprint) plus a native **quick-add sheet**, home-screen **widgets** (the user's pick: header + two wide rounded buttons, each an icon in a tinted circle **plus** its label — "Spent"/"Received", or "Expense"/"Income" for a Budget phone — soft gradient + thin coloured outline; header = household avatar (initial in a circle tinted with the household colour from config) + bold name + "· Hisab/Budget" + to-add badge; default 4×2, resizable; under ~320×110 dp (e.g. 3×1) `large()` uses `widget_quick_compact.xml` — smaller icon circles, labels auto-shrink so wider custom phone fonts don't cut "Received" (user approved from a before/after render, test `widgetSizes`); the small widget stacks icon over label; widgets redraw themselves after an app update via `UpdatedReceiver` (MY_PACKAGE_REPLACED); **manual only — no frequent-entry suggestion chips** (the user removed them; `wPresets` stays hidden, the PRESET action is unused); large: when tall, bank payments to add; small 2×1: the two buttons + a to-add badge), app-icon shortcuts and a quick-settings tile. Package `app.echopdo`, minSdk 26. Installed from `/download/` (sideloaded, not Play Store). **Self-updates** since 1.12 (`Updates.kt`, the user's request, Snaptube-style): every 6 h / on open it checks `/download/version.json`, downloads the APK, verifies SHA-256 + same signing key, installs via `PackageInstaller` (needs "Install unknown apps" once — Phone settings → Updates; first update asks one tap, later ones are silent on Android 12+); `UpdatedReceiver` then posts "updated — tap to open". So `version.json`'s `sha256` must always match the APK (build-release.sh writes both).
- Pairing: ⚙ Settings → **Phone widget** (`PhoneWidget.jsx`, `src/lib/quickDevices.js`) inserts a `quick_devices` row with a one-time 8-char code (SHA-256 stored, 10 min); the app exchanges it via the **`quickadd` Edge Function** (verify_jwt off, auth = device token, SHA-256 stored) for a token scoped to one household: add Hisab/Budget entries, undo its own within 15 min, read picker names (Hisab books/categories/sources, Budget categories/accounts, frequent entries). Each phone has a `default_target` ('hisab' by the user's choice, or 'budget'), editable in the card; the sheet can switch per entry. Unpair = delete the row.
- **Bank SMS capture** (Android 1.2): the phone parses bank SMS itself (`SmsParser.kt`: works for any bank — a generic reader over any DLT sender that needs amount + debit/credit word + masked account/card (or a bank-like header); exact rules for BoB, Federal, ICICI, Kotak run first; tests use made-up values only — never commit the family's real SMS, VPAs, names or account digits) and sends only { direction, amount, date, last digits, card, payee, UPI ref, bank } to `quickadd` action `capture` → table **`captures`** (status new/filed/ignored/matched/transfer, unique (household_id, ref) so both phones can't double it; captures **without** a ref (some card SMS) are deduped server-side on same household + amount + date + direction + last digits + payee, and on the phone by `Store.markSeen` (key = ref or a hash of sender + text — never containing `|`, the list separator; that bug re-sent ref-less SMS on every look-back before 1.6); `match_entry_id` when a same-amount/same-day entry was added by hand in the last day). Filing goes through **`file_capture_as`** (service role only; used by the function) / **`file_capture`** (authenticated wrapper, checks household access) — creates the Hisab entry (source Card/UPI) or Budget transaction and upserts **`capture_rules`** (`payee:<lower payee>` → target/category/account/source/book, `hits`, `auto`; `acct:<bank>:<digits>` → Budget account). **Automatic by default** (user's choice; `quick_devices.auto_capture`, per-phone switch in the Phone widget card): every capture is filed on arrival into the phone's default target — payee's rule, else `guessName()` in the quickadd function (keywords → Food/Groceries/Fuel/Medical/Travel/Shopping/…, only categories the household has; else Other; incoming → Cash in/Refund) — with note = payee (UPI id or name), source Card/UPI, and **without** learning (`p_learn=false`); ones matching an entry added by hand are marked matched. Learning comes from corrections: notification **Change…** (`refile`, learns) / **Remove** (`unfile`), and trigger `private.learn_from_entry()` on hisab_entries.category / transactions.category_id/account_id updates of capture-linked entries (so editing an entry in the web app teaches the payee). With auto off, captures wait for review as before. **Not spending** (1.12): credit-card bill payments ("payment received on your credit card", BBPS, CRED) are skipped on the phone (`SmsParser.isCardBillPayment`); a capture that pairs with an opposite non-card capture of the same amount (±1 day, another account/bank) marks both status **`transfer`** (the earlier one's entry is removed); a payee with `capture_rules.is_self` (set by the notification's **My account** button, action `self`) always becomes `transfer`. Transfer notifications offer "Add anyway". Web: `CaptureInbox.jsx` banner above Home / Entries / Hisab → sheet to ✓ / change / ignore / "Same, skip". Widget config returns `pending` (≤10 new captures with suggestions).
- **Play Protect**: since 1.2 (SMS permissions) Play Protect's enhanced fraud protection *blocks* installing the APK from a browser/file manager ("App blocked to protect your device", no install-anyway). By the user's choice the app stays one APK: they pause Play Protect (Play Store → profile → Play Protect → ⚙ → Scan apps) for each install/update, then turn it back on. The download page explains this.
- Release signing key: `android/release.keystore.enc` (AES-256-CBC, pbkdf2); its password lives in the owner's Vault. `build-release.sh` builds into `public/download/`; `public/.well-known/assetlinks.json` must carry the key's SHA-256. The service worker ignores `/download` and `/.well-known`.
- Tests: Robolectric (`./gradlew testDebugUnitTest`) renders the sheet/widget/pair screens (screenshots via `ECHOPDO_SHOTS`); no emulator here (no KVM). Maven Central 429s from the cloud box — Google's mirror is first in `settings.gradle.kts`.

## Cards & accounts — Hisab ↔ Budget link (Oct 2026)
- Budget **accounts double as instruments**: `accounts.digits text[]` (last digits bank SMS show), `bank`, and for credit cards `statement_day` (cut-off) + `due_day`. Edited in ⚙ → Accounts (`AccountEditor`); **"Found in your SMS"** (`FromSms` in Settings.jsx, rpc `unlinked_instruments`) lists bank+digits from `captures` no account claims → Link to an existing account or create one as Bank / Credit card (`src/lib/instruments.js` `attachDigits`). A closed account / someone else's card can be **Hidden** there (`households.hidden_instruments`, keys `<lower bank>:<digits>`, rpc `set_instrument_hidden`; "Show N hidden" → Unhide). The client reads `sms_instruments` (same rows + `hidden`); `unlinked_instruments` is the older version, left in place.
- Matching: `private.instrument_for(household, bank, digits)` (suffix match, same bank preferred). `hisab_entries.account_id` / `captures.account_id` are set by `file_capture_as`; trigger `accounts_sync_card` (on digits/bank/type/days/name) re-links past captures + entries (`private.relink_instruments`) and, for a card with a statement day, keeps one **auto Plan line** (`recurring_items.auto_card`, "<card> bill", category "Card bills", `expected_amount` 0 — its amount is computed). Typed-in Hisab entries pick it via the **Paid with** chips (web entry sheet; Android quick-add sheet from config `budget.accounts`).
- **Card bills** (`src/lib/cardCycle.js` pure date rules, tests `npm run test:cards`; `src/lib/cards.js` `loadCardBills`): a spend on/before the statement day goes on that statement, later ones on the next; the bill belongs to the month its due date falls in (first due day after the statement). Amount = card's Hisab spends (credits subtract) only — Budget entries on a card are **not** counted (they're usually the bill paid by hand; user's call). Plan shows "N spends so far · closes 15 Oct · due 3 Nov" / "Statement …", tap → the spends.
- **Left to spend** (`src/lib/runway.js` `loadMonthMoney`, Plan current month + Dashboard this month; tap on Plan → `LeftSheet` breakdown) = planned income − Plan commitments (actual if logged, card bills computed) − Hisab spends not on a card − one-off Budget expenses not on a card (user's choices; one-offs on a card count nowhere). Card spends never count now — only on their bill's month.
- **Plan payments from Hisab**: `hisab_entries.recurring_item_id` — trigger `hisab_entries_link_plan` auto-links a spend whose amount equals an unpaid non-card commitment's expected amount (SIP/LIC debits); editable via the entry sheet's **Plan** select. Linked = that item paid ("paid (Hisab)") and not counted again; paid on a card → counted 0 (inside the card bill).
- **Bill payment SMS** (Android 1.16): `SmsParser.billPayment` reads the card side ("payment … received on your … Credit Card XX1234", "thank you for your payment … card ending 1234", and since 1.17 issuers that just say "…CARD", e.g. "Payment of Rs X received for your BOBCARD ending 1234" — before that it fell through to the generic reader and was filed as Cash in); the bank side (debited towards card, CRED, BBPS) stays skipped. `quickadd` `capture` `kind:'bill'` → card by digits (`instrument_for_device`, service-role only) → marks its auto Plan line paid for the bill month (`billMonthPaidOn`), once per month: if the owner already entered the bill by hand (an unlinked expense on that card, dated from 30 days before the payment to the end of the bill month, amount within ±25 %, closest wins) that entry is **taken over** (amount/date/note/category updated, linked; old values kept in `transactions.bill_original`) instead of adding a duplicate (user's request); else a new transaction is inserted. Notification Undo → `unbill` (auto-card payments only) restores a taken-over entry or deletes an inserted one. Unknown card / no bill day → notification asks to set it.

## Auth
Google OAuth (`supabase.auth.signInWithOAuth({ provider: 'google' })`) plus passkeys (`supabase.auth.signInWithPasskey()` / `registerPasskey()`, opted into via `experimental: { passkey: true }` in `src/lib/supabase.js`) — no email/password, no OTP. `src/components/Auth.jsx` offers both; passkeys can only be *registered* once already signed in (Settings → Passkeys), so Google remains the only way to create an account. Google provider redirect URI is `https://rpihmjnvcqnxfketcjit.supabase.co/auth/v1/callback` (Supabase dashboard, Authentication → Providers). Passkeys are bound to a single Relying Party ID/origin (Authentication → Passkeys) — currently the production domain (`echopdo.vercel.app`), so passkey sign-in doesn't work from localhost. The app's own fingerprint credentials (Vault PRF, app lock) are also per-origin: moving domains means re-registering them on each phone.

## Multi-household
One login (the master account) manages several isolated **households** (workspaces) — e.g. "Home", "Parents". Every row in `accounts`/`categories`/`transactions`/`budgets` carries a `household_id` in addition to `user_id`; RLS is by household access (owner or member, see "Household member logins"). The active household is tracked client-side in `src/lib/useFinanceData.js` (persisted to `localStorage`) and threaded through every component as `activeHouseholdId`. Each household has a saved `color` (households.color; `householdColor()` in colors.js, falls back to palette position) used by the topbar chip, the dropdown and the Settings avatars, and editable in the HouseholdSheet; new households get `nextColor`. Switch/create households via the household chip menu in the topbar (`HouseholdMenu` in `src/components/Topbar.jsx`) or manage them in Settings → Households.

## Household member logins
- Settings → Households is a list of household rows (avatar, Active pill, login badge: Fingerprint / PIN only / No login); tapping one opens `HouseholdSheet` (open/switch, rename, family login create/reset/remove, delete — which also removes its login). The owner can give each household its own login there: a **username + 6-digit PIN**. It is a Supabase email/password user with a made-up address `<username>@members.echopdo.vercel.app` (never emailed; moved from the old `members.my-pocket-os…` domain with the eChopdo rename — `members.js` `MEMBER_DOMAIN`, the Edge Function's `EMAIL_DOMAIN`, `seed_new_user` and `block_public_signups` must all agree), `app_metadata.role = 'member'`, created by the **`members` Edge Function** (`supabase/functions/members/index.ts`, deployed with verify_jwt; actions list / create / reset_pin / remove; checks the caller owns the household; uses the auto-injected service role). The PIN stays valid as a backup after fingerprint is on (the user's choice); Reset PIN issues a new one. Removing a login first re-owns the member's rows to the owner (`user_id` FKs cascade on user delete), so no household data is lost.
- `household_members (household_id, user_id, username, fingerprint_at, start_tab)`: written only by the function (client has no insert/delete grant; a member may only update their own `fingerprint_at`; the owner may update `start_tab` — the Budget tab the member's app opens on, set via "Opens on" in the HouseholdSheet; `MemberShell` caches it in `pocketos.memberStartTab` and `BudgetModule startTab` treats it as the home tab for Android back). The **owner** has the same choice per household without a login: `households.start_tab` ("Your app opens on" in the HouseholdSheet); `BudgetModule` lands there on open and on switching household (not while in Settings), and Android back / the ⚙ toggle return to it. `seed_new_user` skips member logins.
- **RLS**: finance tables (accounts, categories, transactions, budgets, recurring_items, dues, due_entries, hisab_books, hisab_entries, hisab_categories) use policy "household rows": `household_id in (select private.my_household_ids())` — households the caller owns or is a member of (`private` schema isn't exposed by the API; security definer). `households`: members can read theirs; only the owner inserts/updates/deletes. Will stays `user_id = auth.uid()` (members can never reach it); `vault_unlockers` / `vault_items` are own-or-member rows for the owner, plus shared-with-my-household reads for members (see Household vaults).
- Client (`src/lib/members.js`): `isMember(session)` → `App` renders `MemberShell` instead of `Shell`: only Budget, no module switcher / Vault / Will long-press, a static household chip (`HouseholdMenu member`), no transfers (one household). After the first PIN sign-in, `FingerprintSetup` turns on the per-device app lock (`useAppLock`, WebAuthn) and stamps `fingerprint_at`; `MemberLockScreen` unlocks with fingerprint or PIN. Settings shows a "Fingerprint unlock" card instead of Households. The sign-in screen has a "Household login" form.
- **Household vaults (shared family vault)**: the owner can **Enable Vault** for a household login (HouseholdSheet; asks the owner's master password → `vault.enableHouseholdVault` inserts a copy of the owner's `password` unlocker under the member's user_id — same master password, same vault key, by the user's choice). The member's `MemberShell` then uses `useVault` like the owner: vault fingerprint gates the whole app (app lock switched off), Budget | Vault switcher, no Will; members can't change the master password or make a recovery code. Sharing is **visibility, not re-encryption**: `vault_items.household_ids uuid[]` — the owner sees every item (own + all members' via `private.my_member_ids()`), a member sees items shared with their household (read-only: RLS lets them read but not update/delete others' rows) plus their own (new member items are tagged with their household). Owner shares per item with the "Share with" chips in the item view; list rows show household dots / "Shared"; a member's view of a shared item says "Shared by <owner's first household name>" (`rpc('family_owner_name')`, security definer, returns only that name). `vault.changePassword` updates every visible `password` unlocker, so household vaults keep the owner's password. Turning a household's vault off deletes its unlockers (their items stay, visible to the owner). `useVault` filters unlockers by the current user id (the owner can also read members'). Will stays owner-only.
- **Sign-ups are closed in SQL**: trigger `block_public_signups` (before insert on `auth.users`, function `private.block_public_signups()`) rejects every new user except member logins: an `@members.echopdo.vercel.app` address with an unexpired one-time row in **`member_signup_tickets`** (RLS on, no client grants; the `members` function writes it just before `createUser`, the trigger consumes it). It can't check `app_metadata.role` — GoTrue sets that *after* the insert, which silently broke every member login created after the block went in (fixed 2026-09-30). New Google/email sign-ups fail with "Database error saving new user"; existing users (the owner) are unaffected. The dashboard's "Allow new users to sign up" toggle is still on — turning it off too is fine. To add another owner account, drop the trigger first.

## Supabase
- Project: `pocketOS`, ref `rpihmjnvcqnxfketcjit`, region ap-northeast-1, Postgres 17.
- URL and publishable key are in `.env` (gitignored). See `.env.example`.
- The schema in `supabase/schema.sql` has already been applied to the remote project, including the multi-household migration at the end of that file.
- Tables: `households`, `household_members`, `member_signup_tickets`, `quick_devices`, `captures`, `capture_rules`, `accounts`, `categories`, `transactions`, `budgets`, `recurring_items`, `dues`, `due_entries`, `hisab_books`, `hisab_entries`, `hisab_categories`, `vault_unlockers`, `vault_items`, `wills`, `will_versions`, `will_log`. Each has `user_id default auth.uid()`; vault/will tables keep one RLS policy, "own rows" (`user_id = auth.uid()`), while the finance tables use "household rows" (see Household member logins). The finance tables (all but `households`, the `vault_*` and the `will*` tables) also have a required `household_id`. The Vault is personal to the login, not per household.
- View `account_balances` (security_invoker) computes current balance per account; carries `household_id` as a trailing column (Postgres `create or replace view` only allows appending columns, not reordering). It counts **all** transactions, including future-dated ones; the Dashboard instead calls `rpc('account_balances_on', { on_date: today() })` (security invoker function) so "today" balances ignore entries dated later (e.g. next month's salary logged from Plan).
- Trigger `on_auth_user_created` → `seed_new_user()` creates a "Home" household plus 12 categories and a Cash account for new users. EXECUTE is revoked from anon/authenticated.
- `rls_auto_enable()` is a Supabase-provided function, not ours. Leave it alone.
- Amounts are always positive; `kind` ('income' | 'expense') decides the sign.
- **Between-household transfers** (`src/lib/transfers.js`, `TransferForm.jsx`, "⇄ Transfer" in the + menu when there are 2+ households): one transfer = an expense in the sender household + an income in the receiver, sharing `transactions.transfer_id`, both in each household's "Home transfer" category (matched loosely so the user's existing misspelled "Home Trasfer " is reused; created if missing). They count in normal income/expense totals by the user's choice. Edit/delete always act on both halves; the Transactions list labels them "⇄ to/from <household>".
- **Dues** (`src/lib/dues.js`, `src/components/Dues.jsx`): money owed between the active household and a person, **both ways** (the user's mother owes relatives, or the user). `dues` = one per person (optional `person_household_id` when the person is one of the user's own households); `due_entries` have `direction` 'out' (money went to the person) / 'in' (came from them), so balance = Σout − Σin (> 0 they owe the household, < 0 it owes them). Entries are mirrored into Budget by default — a transaction in an auto-created "Dues" category, or a ⇄ transfer when `person_household_id` is set — linked by `due_entries.transaction_id` / `transfer_id` (deleting an entry deletes its Budget row; deleting a due keeps them). The opening amount is *not* added to Budget unless ticked (old debts). Optional EMI = a `recurring_items` row with `due_id` (on delete cascade): it shows in Plan, logging it there records the due entry (`addEntry` with `recurringItemId`), and `syncEmi` flips its kind with the balance and deactivates it once settled. Entry labels (Borrowed / Paid back / Lent / Received) depend on the due's first entry.
- **Hisab** (`src/lib/hisab.js`, `src/components/Hisab.jsx`): Money Tracker-style cash books that **don't affect Budget totals** — one `daily` book per household (auto-created on first visit, viewed by month with swipe) plus `occasion` books (Diwali, a wedding…, optional `target`). `hisab_entries`: direction out/in, amount, date, free-text `category` (icon grid from the household's **`hisab_categories`** — managed by the owner in ⚙ → *Hisab categories*: add with an emoji, rename, ↑↓ reorder, remove; seeded once from `CATEGORIES` / `IN_CATEGORIES` via `loadCategories` using an upsert on unique (household_id, direction, name) so concurrent seeds can't duplicate; removing one leaves old entries' text alone; `iconFor` knows the managed icons via `registerIcons`) and `source` (Cash/UPI/Card + custom). The tab opens **straight on Daily** (user's call: daily matters most) — a month card (month picker, big spent, then one row of three: Today / Received / **Balance** = received − spent, Balance only when something was received; no Per day — user's request; occasion books use the same card: ‹ back + name + edit, big spent, target bar if set (its label says "… left" / "over by …"), then Today / Received / Balance). The open occasion book is kept in sessionStorage `pocketos.hisabBook` ({hid, id}) so a reload / pull-to-refresh stays on it; a fresh app start opens Daily with an **📒 Occasions** button (sheet listing occasion books + New book); occasions used in the last 30 days also show as chips under it; an occasion book has ‹ back to Daily. Swipe on the month card changes month; swipe below it switches Daily ↔ Calendar ↔ Summary (`useSwipe`). The entry sheet has a **book row** (🗓️ Daily / 📒 occasions): picking another book moves the entry (how SMS-captured entries, which always land in Daily, get moved to an occasion — one by one, by the user's choice). The Android quick-add sheet shows the same Book row first and keeps a picked occasion for 3 h (`Store.recentBook`). `capture_rules.book_id` only ever keeps a Daily book (trigger `capture_rules_book_daily`), so moving one payment never routes a payee's future payments into an occasion. Entries show **when they happened** (`hisab_entries.occurred_at`, `entryTime()`, under the amount; sorted by it within a day): for SMS payments the SMS's time (phone sends `at` since Android 1.15 → `captures.occurred_at` → copied by `file_capture_as`; a capture read again — Resync — fills a missing time via `fillTime` in quickadd), for entries typed in on the day the time they were added; back-dated entries have none. Never `updated_at`. Book views: Daily (grouped by day), Calendar (heat-tinted month grid, tap a day), Summary (donut by category, by source, received). Entry sheet = calculator keypad (`evaluate` handles + − ×), "Save & next" keeps date/source/category for a run of bills. It must fit one S24 screen **without scrolling, keypad in view** (user's complaint, Oct 2026): amount sits beside Spent/Received, source chips + "Paid with" cards share one horizontal scroll row, the Plan link is a small select at the end of the date/note row, measure at 384×832 before adding anything to it. Category = `CategoryPicker`: a **"Search or add category"** box over a two-row chip strip that scrolls sideways (picked one first, then most used, then the household's order); typing filters, a new name shows **+ Add "…"** (or Enter) → `addCategory` (hisab.js) upserts it into `hisab_categories` at the end with an icon from `guessIcon(name)` (🏷️ if none; changeable in ⚙ → Hisab categories) and picks it — members can add too (household rows RLS). User's request, replacing the tile grid. The Android quick-add sheet does the same since **1.18** (`QuickAddActivity.catSearchField` / `fillCategories`: search box + two-row `HorizontalScrollView`, order from config `hisab.used.{out,in}`; a new name is picked at once and saved via quickadd action **`add_category`** (same `guessIcon` list, seeds the starting set first for a household that never opened Hisab), then appended to the cached config; offline the entry still keeps the name). On the Hisab tab the floating + adds a Hisab entry (to the open book, else it opens Daily with the sheet already up — `openAdd`) instead of opening the Income/Expense menu.
- `budgets` (per-category caps) still exists in the schema but is **unused by the UI** — the Budgets tab was replaced by Plan (see below). Don't build on it without checking with the user first.
- `recurring_items` (name, kind, category, optional account, `expected_amount`, `day_of_month`) power the **Plan** tab (`src/components/Plan.jsx`, replaces the old Budgets tab): a forward-looking view of expected income vs. expected outflow for a chosen month (defaults to next month). `transactions.recurring_item_id` links a logged transaction back to the commitment it fulfilled — the Plan tab shows the actual amount once linked, otherwise falls back to `expected_amount`. Logging an actual also rolls `expected_amount` forward to the new value, since these amounts (credit card dues, etc.) drift month to month.

## UI notes
- **Target device: Samsung Galaxy S24 Ultra** (Chrome, installed PWA): 384 × 832 CSS px at 3.75× — test layouts at 384 px wide. Fingerprint unlock works there (WebAuthn PRF via Chrome).
- **Never use `window.confirm` / `prompt` / `alert`.** Use the in-app dialogs: `const dialog = useDialog()` (`src/lib/dialog.js`, rendered by `DialogProvider` in `src/main.jsx`), then `await dialog.confirm({ title, message, confirmLabel, danger })`, `await dialog.prompt({ title, label, defaultValue })`, `await dialog.alert(message)`. Destructive confirms are red and focus Cancel.
- Colours for categories and accounts come from `src/lib/colors.js` (8-hue palette validated for the dark UI); new ones get the next unused colour (`nextColor`). Accounts have a `color` column (dots in lists). Key chart/legend items by id, never by name (names repeat, e.g. several "Uncategorised").
- Settings cards are **collapsible** (`Collapsible` in Settings.jsx: title + one-line summary when folded, optional header `action`; open/closed remembered per card in `pocketos.settingsOpen`; Households opens by default). New Settings cards should use it.
- Categories are edited (name + colour, or deleted) by tapping the chip in Accounts & Categories (`CategoryEditor` in `Settings.jsx`); kind can't change after creation.
- Accounts are edited (name, type, colour) by tapping the row or its pencil (`AccountEditor` in `Settings.jsx`). Opening balance is hidden in the UI (accounts are spending buckets; the column stays, default 0). Deleting one says how many transactions/plan items use it; those are kept but unlinked (`on delete set null`).
- **Navigation on phones:** a floating pill (`src/components/PillNav.jsx`, One UI style) replaces the old fixed bottom bar in every module: the active tab shows icon + label, others icon only; it hides while scrolling down and returns on scroll up; `withFab` keeps it clear of the + button, which sits beside it on the right. Keep tab labels to one short word.
- **Bottom sheets on phones:** every popup (`.modal-bg > .modal`, including the in-app dialogs) is a bottom sheet under 800 px — slides up, grab handle, sticky action row, drag the top edge down to close (`src/lib/sheetDrag.js`, installed in `main.jsx`; it dispatches a mousedown on the backdrop, which all modals treat as close). Full-height pickers use `.modal.sheet` (no drag). Keep new popups on `.modal-bg` + `.modal` so they get this for free.
- Grids: use `minmax(0, 1fr)` columns (see `.grid2`, `.pk-list`) — plain `1fr` grid items grow to their content and stretched the whole page wider than the phone.
- Dashboard "Coming up" (next month, `ComingUp` in Dashboard.jsx) lists only Plan commitments by day — date tile, name, category · account, amount with "✓ Paid / ✓ Received" or "Expected", plus a done-count bar and "still to pay": ones already logged against a plan item (✓, `recurring_item_id`) and plan items still expected. One-off transactions are left out.
- On phones, the floating + button and pill nav hide while a text field is focused (CSS `:has` in `src/index.css`), and `.content` has extra bottom padding, so the + never covers a Save button.
- **Brand** (Oct 2026, the user's pick from a preview — Cyber Blue felt too vibrant): logo = an **open hisab book with ₹** on the right page and faint ledger lines on the left (`BrandMark` in `src/lib/icons.jsx`; pages #8a98de / #5d6dc4 on charcoal #1a1d21, flat, no glow). Theme **"Slate"**: tokens on `:root` (dark) and `:root[data-theme="light"]` in index.css — `--accent` (text/links), `--accent-bg` + `--on-accent` (solid fills: primary buttons, FAB, module switch), `--accent-2` (soft tint), `--pos/--neg/--warn/--transfer`, `--backdrop`; **no gradients** (`--accent-grad` is kept as a solid alias, `--glow` is empty). Never hard-code colours in new CSS — use the tokens so both themes work. **Appearance** (`src/lib/theme.js`): `pocketos.theme` in localStorage = dark (default) / light / system, applied as `<html data-theme>` + `meta theme-color`; an inline script in index.html applies it before first paint (keep in sync). Icon files: `public/favicon.svg`, `public/icons/source.svg` (rounded) and `maskable.svg` (full bleed, glyph at 78%); the PNGs (`icon-192/512`, `maskable-512`, `apple-touch-icon`) and the Android launcher (`mipmap-xxxhdpi/ic_launcher_foreground|background.png`, glyph at 61% for the adaptive safe zone) + `drawable-nodpi/splash.png` are rendered from those SVGs with headless Chromium — regenerate them if the logo changes. The Android app uses the Slate dark colours (`res/values/colors.xml`, `Ui.kt` `C`, widget drawables); no light theme there. Green/red stay reserved for income/expense (softened: #6fb38f / #d58585 dark, #2c7a52 / #b54848 light).

## Conventions
- Data access happens directly in components via `supabase.from(...)`. Shared loaders are in `src/lib/useFinanceData.js`.
- **Code splitting**: every tab, the Vault screens and the Will module are `React.lazy` in `App.jsx` (wrapped in `Suspense` with the matching skeleton); Recharts lives only in `src/components/Charts.jsx`, used through `LazyCharts.jsx` (same-size placeholder while loading). `preloadBudget()` fetches Home + charts while the unlock screen is up. Main chunk ≈ 500 kB (142 kB gz), was 1.09 MB. Don't import `recharts` anywhere else.
- Money and date helpers are in `src/lib/format.js` (INR / en-IN by default via env). `moneyShort` writes K / L / Cr for en-IN (ICU's compact form says "T" for thousand).
- After any schema change: add the SQL to `supabase/schema.sql`, apply it as a migration, then run the Supabase security and performance advisors.
